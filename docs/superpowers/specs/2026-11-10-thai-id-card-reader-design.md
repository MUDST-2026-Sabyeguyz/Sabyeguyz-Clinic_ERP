# การอ่านบัตรประชาชนไทยด้วยเครื่องอ่านบัตร: การออกแบบ

วันที่: 10 พฤศจิกายน 2026 (Asia/Bangkok)
สถานะ: ร่างสำหรับตรวจ ยังไม่ได้ลงมือเขียนโค้ด
เครื่องอ่านบัตรอ้างอิง: ZOWEETEK ZW-12026-3 (สมาร์ตการ์ด USB)
ที่มา: Requirement + Feedback Update R5 (reader integration) ซึ่ง P2 ระบุว่ายังเปิดอยู่
(`docs/testing/2026-10-14-P2-Patient-Fields-Identity-Lookup.md`)

## 1. เป้าหมายและขอบเขต

เจ้าหน้าที่เสียบบัตรประชาชนที่เครื่องอ่านที่เคาน์เตอร์ แล้วระบบ ERP ทำได้ 2 อย่าง

1. **กรอกฟอร์มลงทะเบียนผู้ป่วยใหม่อัตโนมัติ** จากข้อมูลบนชิปบัตร
2. **ค้นหาผู้ป่วยเดิมด้วยบัตร** แล้วเปิดโปรไฟล์ที่มีอยู่

ตัดสินใจแล้ว

| หัวข้อ | ข้อสรุป |
|---|---|
| ระบบปฏิบัติการเคาน์เตอร์ | Windows, macOS และ Linux |
| เบราว์เซอร์ | Chrome, Edge, Firefox และ Safari |
| การเชื่อมต่อ | โปรแกรมตัวกลางเชื่อมออกไปหา backend แล้วส่งต่อให้หน้าเว็บ (relay) ไม่ให้หน้าเว็บคุยกับเครื่องตัวเองโดยตรง |
| ความยินยอม PDPA | เจ้าหน้าที่กด "อ่านบัตร" ข้อมูลแสดงบนฟอร์มเท่านั้น ต้องติ๊กยินยอม (ช่อง `privacyConsent` เดิม) ก่อนกดบันทึก |
| รูปถ่ายบนบัตร | **ไม่อ่านและไม่เก็บ** |
| ยืนยันตัวตนตอนเช็กอินหรือรับบริการ | **อยู่นอกขอบเขตรอบนี้** |

## 2. ทำไมต้องมีโปรแกรมตัวกลาง และทำไมเลือก relay

- เครื่องอ่านเสียบที่คอมพิวเตอร์หน้าเคาน์เตอร์ เบราว์เซอร์อ่านอุปกรณ์สมาร์ตการ์ดตรงๆ ไม่ได้ และเซิร์ฟเวอร์ก็เข้าถึง USB ของเครื่องเคาน์เตอร์ไม่ได้
- ทางเลือกที่ให้หน้าเว็บเรียก `127.0.0.1` ตรงๆ ใช้ได้กับ Chrome/Edge/Firefox แต่ Safari บล็อกการเรียก HTTP ภายในเครื่องจากหน้า HTTPS จึงต้องออกและติดตั้งใบรับรองภายในเครื่อง ซึ่งติดตั้งยากและเปราะบาง
- relay ผ่านเซิร์ฟเวอร์ทำให้ทุกเบราว์เซอร์ทำงานเหมือนกัน และตัวกลางไม่ต้องติดตั้งใบรับรอง

```
เครื่องอ่านบัตร (USB, PC/SC)
        │
โปรแกรมตัวกลาง (ถาดระบบ Windows/macOS/Linux)
        │  WebSocket ออกไปหา backend (TLS, โทเคนประจำเครื่อง)
        ▼
Backend (Spring Boot) ── ฐานข้อมูล (เครื่องอ่าน, ประวัติการอ่าน)
        │  SSE ผลการอ่าน (ส่งครั้งเดียวให้ผู้สั่ง)
        ▼
หน้าเว็บ ERP (Vue)  ลงทะเบียนผู้ป่วย / ค้นหาผู้ป่วย
```

## 3. ส่วนประกอบ

### 3.1 โปรแกรมตัวกลาง (id-card-agent)
- อ่านชิปผ่าน PC/SC ใช้ไลบรารีมาตรฐานของภาษาที่เลือกในขั้นวางแผน (เอนไปทาง Java ด้วย `javax.smartcardio` เพราะทีมใช้อยู่แล้ว ต้องยืนยันว่าทำงานบน macOS รุ่นใหม่ได้) แพ็กเป็นตัวติดตั้งของแต่ละระบบ
- เชื่อมต่อ backend ด้วย WebSocket อัตโนมัติ เชื่อมใหม่เมื่อหลุด รายงานสถานะเครื่องอ่าน (ออนไลน์, พบเครื่องอ่าน, มีบัตร)
- อ่านเมื่อ backend สั่งเท่านั้น รอบัตรไม่เกิน 30 วินาที **ไม่เก็บข้อมูลลงดิสก์และไม่เขียนข้อมูลบัตรลง log**
- ไม่อ่านรูปถ่าย

### 3.2 Backend (เพิ่มในโมดูลใหม่ `idcard`)
- จัดการเครื่องอ่าน (เฉพาะผู้จัดการ) ออกรหัสจับคู่ใช้ครั้งเดียว เก็บโทเคนเครื่องเป็นค่าแฮช เพิกถอนได้
- รับการเชื่อมต่อ WebSocket จากตัวกลาง ตรวจโทเคน
- รับคำขออ่านจากหน้าเว็บ ส่งคำสั่งไปตัวกลาง รับผลแล้วส่งต่อด้วย SSE ให้ผู้สั่งเท่านั้น
- ผลอยู่ในหน่วยความจำ 60 วินาที ส่งได้ครั้งเดียวแล้วลบ
- โหมดค้นหา: backend ค้นผู้ป่วยจากเลขบัตรเอง ส่งกลับเฉพาะผลค้น
- ตรวจเลขบัตรด้วยหลักตรวจสอบ (checksum) ฝั่งเซิร์ฟเวอร์ เพิ่มจากการตรวจ 13 หลักเดิม
- บันทึกประวัติการอ่าน (ใคร, เมื่อไหร่, เครื่องไหน, วัตถุประสงค์, ผลสำเร็จหรือไม่) **ไม่เก็บข้อมูลบัตร**

### 3.3 หน้าเว็บ (Vue)
- ตัวช่วยรวมศูนย์ `useIdCardReader` จัดการสถานะ: ยังไม่ได้เลือกเครื่อง, ตัวกลางออฟไลน์, ไม่พบเครื่องอ่าน, รอบัตร, กำลังอ่าน, สำเร็จ, ผิดพลาด
- ปุ่ม "อ่านบัตร" ที่หน้าลงทะเบียนผู้ป่วยใหม่ (`PatientRegistrationView`) และหน้าค้นหาผู้ป่วย (`PatientSearchView`)
- เลือก "เครื่องอ่านบัตรของฉัน" ได้ในเบราว์เซอร์ จำค่าไว้ในเบราว์เซอร์ ถ้าสาขามีเครื่องออนไลน์เครื่องเดียวให้เลือกอัตโนมัติ
- หน้าตั้งค่าสำหรับผู้จัดการ: เพิ่มเครื่อง, ดูรหัสจับคู่, เพิกถอน, ดูสถานะออนไลน์
- ถ้าอ่านบัตรไม่ได้ เจ้าหน้าที่พิมพ์ข้อมูลเองได้ตามเดิมเสมอ

## 4. การไหลของข้อมูล

### 4.1 จับคู่เครื่อง (ครั้งเดียวต่อเครื่อง)
1. ผู้จัดการสร้างเครื่องอ่านในหน้าตั้งค่า (ชื่อ, สาขา) ได้รหัสจับคู่ที่ใช้ครั้งเดียวและหมดอายุภายในเวลาจำกัด
2. ติดตั้งตัวกลางที่เครื่องหน้าเคาน์เตอร์ ใส่รหัสจับคู่ ตัวกลางได้โทเคนประจำเครื่อง
3. ตัวกลางเชื่อม WebSocket ไปหา backend ด้วยโทเคน

### 4.2 ลงทะเบียนผู้ป่วยใหม่ (วัตถุประสงค์ REGISTER)
1. เจ้าหน้าที่กด "อ่านบัตร" หน้าเว็บส่ง `POST /api/id-card/reads` (เครื่อง, วัตถุประสงค์) backend ผูกคำขอกับผู้ใช้ที่ล็อกอินและสาขา
2. backend ส่งคำสั่งอ่านไปตัวกลาง ตัวกลางรอบัตร อ่านชิป ส่งผลกลับ
3. backend ส่งผลให้หน้าเว็บของคำขอนั้นผ่าน SSE (`GET /api/id-card/reads/{id}/events`) แล้วลบทิ้ง
4. หน้าเว็บเติมฟอร์ม เจ้าหน้าที่แก้ไขได้ ต้องติ๊กยินยอมก่อนบันทึก

### 4.3 ค้นหาผู้ป่วยเดิม (วัตถุประสงค์ LOOKUP)
ขั้นตอนเดียวกัน แต่ backend นำเลขบัตรไปค้นด้วย `PatientRepository.findByNationalId` เองแล้วส่งกลับเฉพาะ `{พบ, รหัส HN, ชื่อ}` หรือ `{ไม่พบ}` หน้าเว็บไม่ได้รับข้อมูลส่วนตัวจากบัตร ถ้าไม่พบ ให้ถามว่าจะลงทะเบียนใหม่ไหม (ตอนนั้นอ่านบัตรอีกครั้งตามข้อ 4.2)

## 5. ข้อมูลที่อ่านจากชิปและการแปลงลงฟอร์ม

ชุดคำสั่ง (APDU) เลือกแอปเพล็ตบัตร AID `A0 00 00 00 54 48 00 01` แล้วอ่านทีละช่วง ข้อมูลข้อความเป็น TIS-620 ใช้ `#` คั่น วันที่เป็น พ.ศ. รูปแบบ `YYYYMMDD` **คำสั่งอ่านแต่ละช่วงมาจากแนวปฏิบัติของชุมชน ไม่ใช่เอกสารทางการ ต้องยืนยันกับบัตรจริงทั้งแบบ T=0 และ T=1 ก่อนถือว่าถูกต้อง**

| จากบัตร | ลงฟอร์ม (`PatientRegistrationForm`) |
|---|---|
| เลขบัตร 13 หลัก | `identityNumber`, `identityDocumentType` = บัตรประชาชน |
| ชื่อไทย `คำนำหน้า#ชื่อ#ชื่อกลาง#นามสกุล` | `title` (ดูกฎด้านล่าง), `firstName`, `middleName`, `lastName` |
| ชื่ออังกฤษ | `fullNameEnglish` |
| วันเกิด `YYYYMMDD` (พ.ศ.) | `birthDate` (ค.ศ. = ปี − 543) |
| เพศ `1`/`2` | `gender` = ชาย/หญิง (เลือกจากเพศบนบัตร ไม่เดาจากคำนำหน้า) |
| ที่อยู่ `เลขที่#หมู่#ตรอก#ซอย#ถนน#ตำบล#อำเภอ#จังหวัด` | `address` ต่อกันเป็นข้อความเดียว ไม่เกิน 255 ตัวอักษร |
| วันออกบัตร / วันหมดอายุ | ใช้ตรวจบัตรหมดอายุ ไม่เก็บ `99999999` = ตลอดชีพ |
| (ไม่มีบนบัตร) | `phone` เจ้าหน้าที่กรอกเอง |

กำหนดค่าคงที่: `nationality` = ไทย, `customerType` = Thai

กฎคำนำหน้า: นาย/นาง/นางสาว/เด็กชาย (ด.ช.)/เด็กหญิง (ด.ญ.) แปลงเป็นค่ามาตรฐานของระบบ คำนำหน้าอื่น (เช่น ยศ) ไม่เดา ให้เจ้าหน้าที่เลือกเอง

## 6. การเปลี่ยนแปลงฐานข้อมูลและ API

ตารางใหม่ (migration ใหม่ ไม่แก้ migration เดิม)
- `card_reader_workstation`: รหัส, ชื่อ, สาขา, แฮชโทเคน, แฮชรหัสจับคู่, เวลาหมดอายุรหัส, สถานะ (ใช้งาน/เพิกถอน), เวลาออนไลน์ล่าสุด
- `id_card_read_audit`: รหัส, เครื่อง, ผู้ใช้, สาขา, วัตถุประสงค์, ผล (สำเร็จ/หมดเวลา/ผิดพลาด), เวลา **ไม่มีคอลัมน์ข้อมูลบัตร**

API ใหม่ (ทั้งหมดต้องล็อกอิน ยกเว้นช่องทางของตัวกลาง)
- ผู้จัดการ: เพิ่ม, แสดง, เพิกถอนเครื่องอ่าน, ออกรหัสจับคู่ใหม่
- เจ้าหน้าที่: แสดงเครื่องของสาขา, `POST /api/id-card/reads`, `GET /api/id-card/reads/{id}/events`
- ตัวกลาง: จับคู่ด้วยรหัสแล้วรับโทเคน, WebSocket สำหรับคำสั่ง-ผล

ไม่แก้ตาราง `patient` เพราะมีฟิลด์ที่ต้องใช้ครบแล้ว (`national_id`, ชื่อ, ชื่อกลาง, วันเกิด, เพศ, ที่อยู่, สัญชาติ)

## 7. ความปลอดภัยและความเป็นส่วนตัว

- TLS ตลอด รหัสจับคู่ใช้ครั้งเดียวและหมดอายุเร็ว โทเคนเครื่องเก็บเป็นแฮชและเพิกถอนได้
- สั่งอ่านได้เฉพาะผู้ใช้ที่ล็อกอิน เครื่องต้องอยู่สาขาเดียวกับผู้ใช้ จำกัดจำนวนคำขอต่อนาที
- ผลการอ่านส่งได้ให้ผู้สั่งคนเดียว ครั้งเดียว ภายใน 60 วินาที แล้วลบทันที
- ไม่บันทึกข้อมูลบัตรลง log, ฐานข้อมูล หรือดิสก์ในขั้นอ่าน ข้อมูลลงฐานข้อมูลเมื่อกดบันทึกลงทะเบียนเท่านั้น ในฟิลด์เดิมของผู้ป่วย
- ต้องติ๊กยินยอมก่อนบันทึก (ใช้ `@AssertTrue privacyConsent` เดิมในคำขอลงทะเบียน)
- ประวัติการอ่านบันทึกเฉพาะข้อมูลเมตา

## 8. การจัดการข้อผิดพลาด

| สถานการณ์ | พฤติกรรม |
|---|---|
| ตัวกลางออฟไลน์ | แจ้งให้ตรวจโปรแกรมตัวกลาง ปุ่มกรอกเองยังใช้ได้ |
| ไม่พบเครื่องอ่าน | แจ้งให้เสียบเครื่องอ่าน |
| ไม่ใส่บัตรใน 30 วินาที | หมดเวลา ให้กดอ่านใหม่ |
| บัตรอ่านไม่ได้ / แอปเพล็ตไม่รองรับ | แจ้งผิดพลาด ให้ลองใหม่หรือกรอกเอง |
| เลขบัตรไม่ผ่านหลักตรวจสอบ | ไม่เติมฟอร์ม แจ้งผิดพลาด |
| บัตรหมดอายุ | เตือน แต่ไม่บล็อก (เปลี่ยนเป็นบล็อกได้ถ้าคลินิกต้องการ) |
| อ่านบัตรของเครื่องอื่น/สาขาอื่น | ปฏิเสธ |

## 9. การติดตั้งโปรแกรมตัวกลาง

- ตัวติดตั้ง: Windows `.msi`, macOS `.pkg`, Linux `.deb` (ระบุ dependency `pcscd`) เปิดอัตโนมัติตอนเข้าเครื่อง มีไอคอนสถานะที่ถาดระบบ
- Windows และ macOS มีตัวอ่านสมาร์ตการ์ดในระบบ Linux ต้องมี `pcscd`
- ถ้าไม่มีใบรับรองลายเซ็นโปรแกรม Windows จะขึ้นเตือน SmartScreen และ macOS จะขึ้นเตือน Gatekeeper ต้องกดอนุญาตเอง คู่มือติดตั้งต้องระบุขั้นตอนนี้ การซื้อใบรับรองเป็นการตัดสินใจแยกของคลินิก
- ไม่รวมการอัปเดตอัตโนมัติในรอบแรก

## 10. การทดสอบ

- **ตัวกลาง:** ข้อมูลบัตรจำลอง ทดสอบถอดรหัส TIS-620, แยก `#`, แปลง พ.ศ., ที่อยู่ยาวเกิน 255, วันหมดอายุ `99999999`, บัตรเสีย
- **Backend:** checksum เลขบัตร, จับคู่และเพิกถอนเครื่อง, ผลส่งได้ครั้งเดียวและหมดอายุ, ผู้ใช้หรือสาขาอื่นรับผลไม่ได้, ประวัติการอ่านไม่มีข้อมูลบัตร, จำกัดอัตราคำขอ, โหมด LOOKUP ไม่คืนข้อมูลส่วนตัว
- **หน้าเว็บ:** สถานะของ `useIdCardReader` ด้วย SSE จำลอง, การเติมฟอร์ม, ลำดับยินยอมก่อนบันทึก
- **ครบวงจร:** Cypress กับตัวกลางจำลองที่เชื่อม backend ทาง WebSocket
- **เครื่องจริง:** ทดสอบกับ ZW-12026-3 และบัตรจริงของเจ้าของบัตร

ตารางการรองรับ (บันทึก "รองรับอย่างเป็นทางการ" เฉพาะชุดที่ทดสอบจริงแล้ว)

| ระบบ | เบราว์เซอร์ | สถานะเมื่อเริ่ม |
|---|---|---|
| Windows | Chrome, Edge, Firefox | ทดสอบได้ในเครื่องพัฒนา |
| macOS | Safari, Chrome | **ต้องมีเครื่อง macOS ให้ทดสอบ** |
| Linux | Firefox, Chrome | **ต้องมีเครื่อง Linux ให้ทดสอบ** |

## 11. ความเสี่ยงและสิ่งที่ต้องยืนยัน

1. **ชุดคำสั่งอ่านชิป** (ข้อ 5) ต้องยืนยันกับบัตรจริง ทั้งบัตร T=0 และ T=1 และบัตรรุ่นต่างอายุ
2. **ZW-12026-3** ควรใช้ไดรเวอร์ในตัวของระบบ (CCID) ได้ ยังไม่ได้ลองกับเครื่องจริง
3. **ไลบรารีสมาร์ตการ์ดของ Java บน macOS รุ่นใหม่** เคยมีรายงานปัญหาการหา PC/SC ต้องยืนยันหรือเลือกภาษาอื่น
4. **ไม่มีเครื่อง macOS/Linux/Safari ให้ทดสอบ** การรองรับเต็มรูปแบบต้องอาศัยเครื่องจริงจากทีมหรือคลินิก
5. **ข้อมูลบัตรผ่านเซิร์ฟเวอร์ชั่วคราว** (relay) เป็นข้อแลกเปลี่ยนของการรองรับทุกเบราว์เซอร์ ควรให้ผู้รับผิดชอบเรื่อง PDPA ของคลินิกตรวจแนวทางนี้
6. **คำนำหน้าบนบัตร** ที่นอกเหนือ 5 กลุ่ม (ยศ, ฐานันดร) ตั้งใจไม่เดา อาจมีผู้ป่วยบางกลุ่มที่ต้องเลือกเอง
