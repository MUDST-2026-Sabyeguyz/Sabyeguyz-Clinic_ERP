## Correctness review / remaining risk

- Old Chat2 coverage has shifted interpretations at 098.04 and many 101.xx. The exact AC text below is authoritative; suite names/counts do not establish AC completion.
- Refund bug confirmed and corrected: purchaser-only refund rights (099.01/100.01), rather than purchaser-first then recipient fallback. Original multi-holder cancellation restoration remains supported for historical records. No data migration or rewriting existing cancellation rows.
- Paid reversal takes course -> usage -> existing component payout locks (sorted payout ID), with refreshed statuses. Existing payout pay locks branch/month -> payout then finalizes closing; it does not lock courses in finalizeClosing. No obvious current course/payout lock cycle found, but concurrent payout confirmation versus reversal is not explicitly tested. Cross-staff latest-Paid-month selection can race a different future payout; pending correction remains unapplied and application workflow rechecks target status. Treat this as unproven concurrency coverage.
- All-Paid correction appends a zero reversal marker: keeps paid source totals intact but marks original inactive in currentAllocation. Reversed usage is excluded from settle/recalculate. Mixed-paid correction negates unpaid component only; Closed unpaid payout must be Reopened because pay() recomputes totals and rejects changed amounts. Prior Paid rows are never refreshed by prepare().
- Receipt payment and payout payment are different domains. These tests never claim actual bank transfer or automatic deduction. New adjustments remain Pending and require Manager approval plus deduction consent/reference in existing application flow.
- Adjustment externalReview service alone sets status, but CommissionPayrollController records actor/time in audit_log. Updated AdjustmentLifecycleHttpTest asserts this audit row; await the corrected run before promoting108.02.
